# 直径ベースの塗布量校正

点塗布したペーストを真上から撮り、写った円の直径から塗布体積を推定する。CNN による
推定（[画像ベース吐出量推定](image-based-dispense-calibration.md)）より先に試す簡易な
手法で、装置に torch を持ち込まずに動く。

## なぜ直径で足りるのか

収集済みデータ 6 session / 831 サンプル / 4,155 画像で手法を比較した。指標は session 内
の点ごと相対残差（小さいほど良い）。

| 手法（view 集約は中央値）                    | blank 誤検出 | 検出失敗 | session 内残差 |
| -------------------------------------------- | -----------: | -------: | -------------: |
| 固定閾値 25                                  |         0/18 |        0 |          0.139 |
| 比率 20%                                     |         0/18 |        0 |          0.129 |
| Otsu 単体                                    |    **12/18** |        0 |          0.122 |
| **Otsu + 最小コントラスト 20 + view 中央値** |     **0/18** |    **0** |      **0.122** |

Otsu 単体は blank セルの背景ノイズを拾って 18 個中 12 個を誤検出する。差分の分位点が
最小コントラストに届かない時点で打ち切る blank ガードを前置すると、精度を落とさずに
誤検出が消える。これを採用する。

### 差分をこれ以上使い込んでも効かない

pre/post の差分が得られるので、直径だけでなく差分の強度も使えば精度が上がるはずだ、
という仮説を実測で確かめた。結果は否定的。

| 試した使い方                                 | session 内残差 | 判定                               |
| -------------------------------------------- | -------------: | ---------------------------------- |
| 差分強度の積分 S のみ                        |          0.380 | 大幅に劣る                         |
| 直径 3 次 + S                                |          0.114 | 点ごとは微改善だが総体積誤差は悪化 |
| 半値幅・強度重み付き面積・2 次モーメント直径 |   0.132〜0.139 | いずれも面積等価直径に及ばない     |

理由は残差 0.080 の内訳にある。

| 要因                                                   | 寄与                |
| ------------------------------------------------------ | ------------------- |
| 同一指令量の点どうしのばらつき＝**実際の吐出ばらつき** | 0.054（分散の 45%） |
| 塗布順の線形ドリフト                                   | 分散の 23%          |
| **view 間ばらつき＝画像測定ノイズ**                    | **体積換算 1.2%**   |

画像からの直径測定は既に測定ノイズ 1.2% に達している。差分の使い方を詰めて改善できる
のはこの 1.2% だけで、残差の大半は「教師ラベルが指令量比例で点ごとの実ばらつきを持た
ない」ことと吐出ドリフトに由来し、モデル側では埋められない。

差分そのものは blank ガード・銅板ヘアラインの除去・照明ムラの局所補正に不可欠なので、
pre/post 画像は従来どおり保存する。

## パイプライン

`pcbasm.pasting.paste_volume` に置く。OpenCV / numpy は base dependencies なので
Raspberry Pi の WebAPI プロセスでそのまま動き、`ml-runtime` も torch も要らない。

### 1 view の直径計測（`detect.py`）

1. pre − post をグレースケールで取り、暗くなった側だけを 0〜255 に clip する
2. 差分の 99 パーセンタイルが `min_contrast`（既定 20）未満なら**直径 0** で終える
    （blank ガード）
3. Otsu 閾値を求め、`min_contrast × threshold_floor_ratio` を下限として 2 値化する
4. 3×3 の MORPH_OPEN で孤立点を落とす
5. 最大連結成分の面積が `min_area_px` 未満なら直径 0
6. 面積等価直径 `2√(area/π) / pixel_per_mm` を mm で返す

「はんだが写っていない」は**正常系**で、`detected=False` / `diameter_mm=0.0` を返す。
`(None, 理由)` を返すのは構造的な不正（shape 不一致・3 channel でない・`pixel_per_mm`
が非正・ハイパラが不正）だけ。

引数は OpenCV の **BGR** を受ける（`cv2.imread` の出力そのまま）。

### view の集約（`aggregate.py`）

検出できた view の**中央値**に固定する。被覆域で単調なモデルなら、view 数が奇数の
とき「view ごとに推定して中央値を採る」ことと「直径を集約してから 1 回モデルへ通す」
ことが厳密に一致する。偶数のときは中央 2 つの平均になるため 2 次以上のぶんだけ差が
出るが、実素材の view 間ばらつき（相対 0.2% 程度）では相対 1e-4 未満で実害はない。

マルチ view の主目的は**検出失敗時のフォールバック**であって測定精度の底上げではない。
検出できなかった view は中央値の母数から外す。

### 周辺 view の既定は 0（中心のみ）

実測では**周辺 view に利点がほぼ無い**ことが分かったので、`view_count` の既定は 0 にした。

| 期待していた役割           | 実測                                                            |
| -------------------------- | --------------------------------------------------------------- |
| 検出失敗時のフォールバック | 831 サンプルで**検出失敗 0 件**。一度も発火していない           |
| 直径測定の精度向上         | view 間ばらつき（1 view あたりの測定ノイズ）が体積換算 **1.2%** |

1.2% を中央値で 5 view 分畳んでも約 0.5% までしか下がらない。総残差 8.0% の大半は実吐出
ばらつきと塗布順ドリフトなので、5 view → 1 view で**総残差は 8.0% → 8.1% 程度**しか動か
ない。実素材の view 間相対差も 0.2〜1.1% だった。

対する費用は撮影枚数そのもので、収集時間は撮影パスが支配する。144 セルなら 5 view で
1440 枚、中心のみなら 288 枚。

**周辺 view を増やす価値があるのは CNN 方式の学習材料を採るときだけ。**
[要件書](image-based-dispense-calibration.md)は共有 CNN で各 view を符号化して平均集約
する設計で view dropout も前提にしているが、そこでも「達成条件は 1 view でも成立させる」
としている。

### モデル（`model.py`）

切片 0 固定の 3 次。

```
V = a·d³ + b·d² + c·d
```

切片列を持たないので `V(0) = 0` が構造的に保証され、blank（直径 0 → 体積 0）を厳密に
満たす。純 3 次（`a·d³` のみ）は残差 0.124 で不足し、3 項すべて要る。

`numpy.linalg.lstsq` で解く。blank の (0, 0) は設計行列上ゼロ行なのでフィットには
入れず、誤検出の検査にだけ使う。次の場合は係数を返さず理由を返す。

- 正の直径が 3 点未満
- 直径がすべて同値
- 被覆域内で `V(d) <= 0` になる

被覆域内の単調性は診断へ記録する（上の集約の等価性の前提であるため）。

### 推定（`estimator.py`）

具象クラス `DiameterVolumeEstimator` ひとつ。Protocol も ABC も作らない。直径以外の
手法が来たときは並存ではなく置き換わる公算が高い。

不採用は例外にせず理由文字列にする。

| 理由                               | 意味                                       |
| ---------------------------------- | ------------------------------------------ |
| `no_views`                         | view を 1 つも渡していない                 |
| `no_deposit_detected`              | 全 view で検出できなかった（blank を含む） |
| `diameter_out_of_calibrated_range` | 被覆域の外なので外挿になる                 |
| `image_invalid: <理由>`            | 構造的不正（呼び出し側のバグ）             |

推定の標準偏差は校正時に記録した相対残差から与える。直径方式には 1 点ごとの不確かさ源
が無いので、分布としての当てはまり具合を使うのが唯一の筋。

条件（ペースト・ノズル径・塗布高さ・撮影スケール）の照合は**推定器では行わない**。
断ってしまうと条件不一致の session を評価すること自体ができなくなるため、照合して
報告するのは評価側の責務とする。

## 校正ファイル

`data/paste-volume-calibrations/<slug>.paste-volume.json`。1 校正 = 1 session = 1 ファイル
で、WebUI から明示的に選ぶ。Git 管理する（装置設定と同じく再現に要る資産）。

```json
{
  "kind": "pcbasm-paste-volume-diameter-calibration",
  "schema_version": 1,
  "created_at": "...",
  "label": "S3X70-E150DN / n0.30 / h0.20",
  "conditions": { "paste_id": "...", "nozzle_diameter_mm": 0.3, "paste_height_mm": 0.2,
                  "pixel_per_mm": 28.678, "crop_size_px": 53, "...": "..." },
  "detection": { "kind": "diameter_otsu_v1", "min_contrast": 20.0, "...": "..." },
  "model": { "kind": "cubic_through_origin", "cubic_ul_per_mm3": 0.0, "...": "..." },
  "source": { "session": "...", "label_kind": "rotation_allocated", "...": "..." },
  "diagnostics": { "blank_false_positive_count": 0, "total_relative_error": 0.0, "...": "..." }
}
```

- **検出ハイパラは校正と不可分**。違うハイパラで測った直径に係数を当てても意味がない
    ので、`detection` は校正へ埋め込み、**キーの欠落も拒否**する（既定値で黙って埋めると、
    既定値を将来変えたときにキーを欠いた既存ファイルの意味が静かに変わる）
- `source` は**単数**。マルチセッションには対応しない
- 版違いは移行せず拒否する（dataset metadata と同じ方針）

## 達成条件が「session 総体積の誤差」である理由

教師ラベル `label.kind = "rotation_allocated"` は、電子天秤で計った総質量を**指令回転数
比で配分**した値であり、点ごとの真値ではない（ラベル = 指令量 × 定数）。したがって
点ごとの ±10% は直径方式でも CNN でも原理的に評価できない。

- **主基準: session 総体積の相対誤差**（運転時補正が必要とする集約係数に対応）
- 点ごと誤差は参考値として診断に併記する
- **blank の検出直径 0 と検出失敗 0 を回帰条件**とする

既存データでの LOSO 実測は総体積誤差の中央値 2.7% / 最悪 8.8%。1 session 完結のほうが
精度も良い（session 内 0.122 < LOSO 0.146）ので、マルチセッションには対応しない。

## WebUI

運転者の目的は「校正を作ること」なので、**収集と生成を 1 ページに閉じる**。収集の終わりに
別ページへ移って session を選び直させない。

| ジョブ                                                              | 役割                                                                                                                            |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **`paste_volume_calibration`**（塗布量校正の生成。実機・約 1 時間） | 収集 → 確定 → フィット → 診断 → 保存までを 1 回の実行で通す。既存の校正を指定すれば、その校正での推定 vs 実測の誤差も同時に出る |
| `paste_volume_refit`（塗布量校正の再フィット。装置不要・数秒）      | 収集済み session を選び、**検出ハイパラを変えて校正を作り直す**                                                                 |

分けているのはハイパラ調整のためだけ。`uses_machine` はジョブ定義の静的フラグなので、
1 つのジョブでは「装置を使う/使わない」を切り替えられない。再フィットを畳んでしまうと、
ハイパラを 1 つ変えるたびに実機と 1 時間とペーストが必要になる。

再フィットは装置を使わず数秒で終わるので、**実行そのものが検出ハイパラのプレビュー**に
なる。どちらのジョブも `save_name` を空にすると診断だけを出して Git 管理の保存先を汚さない。

**校正が作れなくても収集は失敗させない。** blank 誤検出などでフィットを断ったときも、
この時点で 1 時間の収集と計量は終わっているので dataset は残し、警告に留める。ハイパラを
変えて再フィットから作り直せる。

収集した dataset は副産物として残り、CNN 方式の学習材料にもなる。

判定・集計・誤差計算はすべて `pcbasm.pasting.paste_volume` にあり、ジョブと router は
入出力変換・prompt・progress・artifact 変換だけを担う（skill `webui-thin-wrapper`）。
