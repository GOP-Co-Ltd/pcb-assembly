# ピンセット式 PnP の運動制御

部品実装（`[pnp]`）の機体の、運動制御の設計案。
XYZ ステージの制御方式と、ピンセットのサーボ、強化学習（RL）の置き場所を扱う。

状態は**提案**で、実装には着手していない。
方式の最終判断は、[進め方](#%E9%80%B2%E3%82%81%E6%96%B9)の段階 1 で実測してから行う。

## 前提

この機体は、一般の PnP 機のようにノズルとエアで部品を吸着しない。
**ピンセットで部品をつかみ、基板に置く**。人がピンセットで部品を置く動作を、機械で行う。

| 項目       | 構成                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| 自由度     | 4+1。XYZ と、ピンセットの回転（θ）で 4 軸、ピンセットの開閉で 1             |
| XYZ        | stepper。台形ネジ（1.5 mm/rev）の直動。いまは Klipper で駆動する            |
| MCU        | BTT SKR Pico（RP2040、TMC2209 × 4）。塗布機と同じボード                     |
| θ・開閉    | Feetech STS3032 を 1 台ずつ。FEETECH URT-2 経由の UART で Raspberry Pi へ   |
| 接触の検知 | ロードセル（HX711、80 SPS）。いまは Klipper の `[load_cell_probe]`          |
| カメラ     | 2 系統。位置合わせ用のトップカメラと、ステージ全体を見渡すフロント RGB 広角 |

吸着ノズル・負圧・ノズル交換といった吸着式の概念は持ち込まない。
部品の保持と解放は、ピンセットの開閉（つかむ・離す）として扱う。

## 要件

- **R1 連続指令。** 「G-code を送り、着くまで待ち、止まる」ではなく、
    「速度 v で動き続け、指令が変わればすぐ従う」動かし方をしたい。
    人がコントローラで操作するのと同じ形で、機械も操作する
- **R2 接触停止。** ツールヘッドが何かに接触したことをロードセルで検知したら、即時に止める。
    これはエラーではなく、ただ止まる。止まったあとも、そのまま運転を続けられる
- **R3 RL で制御する。** 制御の多くを RL（と模倣学習）で作る。
    そのため、指令と観測が固定周期でやりとりでき、その遅延が一定であること

R1 と R2 は、RL のポリシーが何を出しても機体を壊さないための安全層も兼ねる。

### 数値で決める項目

次の値は未決定。表の「仮置き」は議論の出発点で、段階 1 の実測の前にユーザーと決める。

| 項目                       | 仮置き                         | 決め方                                         |
| -------------------------- | ------------------------------ | ---------------------------------------------- |
| 制御周期（指令・観測）     | 50 Hz                          | RL のポリシーの推論時間とカメラの fps で決める |
| 指令から動き出すまでの遅延 | 40 ms 以下で、ばらつきが小さい | 学習時と実機のずれが出ない範囲                 |
| 接触から停止までの時間     | 20 ms 以下                     | 部品と基板を傷めない押し込み量から逆算         |
| 最大速度                   | 10 mm/s（今の `max_velocity`） | 機構で決まる                                   |

## Klipper で満たせるか

以下は Klipper の設計についての理解で、段階 1 の実測で確かめる。

- **R1 に合わない。** Klipper は移動を「少し先の時刻」に予約し、先読みで速度をつなぐ。
    短い `G1` を流し続けると、バッファの分だけ遅延が積み上がるか、
    キューが空になって区間ごとに減速・停止する
- **予約した移動を、途中で減速停止して取り消せない。** 止める手段は `M112` だけで、
    これはシャットダウンになり `FIRMWARE_RESTART` が要る。R2 の「エラーではなく止める」にならない
- **R2 は homing と probing の間しか効かない。** `[load_cell_probe]` の `PROBE` 中は
    MCU の中で即時に止まるが、任意の移動の途中ではこの仕組みを使えない

接触停止は MCU の中で完結させる必要がある。Pi の Python でロードセルを見張って止めると、
Linux のスケジューリングで数十 ms 単位の遅れが出得る。

## 方式の比較

| 方式                                  | R1                                      | R2                           | 費用・リスク                                         |
| ------------------------------------- | --------------------------------------- | ---------------------------- | ---------------------------------------------------- |
| A. Klipper のまま                     | 短い区間の連続送信で近似。遅延が課題    | probing 中だけ               | 最小。既存コードがそのまま使える                     |
| B. grblHAL（RP2040 版）を SKR Pico へ | ジョグ（`$J=`）と取り消しで大半を満たす | 移動中の接触停止は改造が要る | 既製の動作実績。ただし改造すると保守を抱える         |
| C. 自作ファームを SKR Pico へ         | 速度指令のストリームとして設計する      | MCU の中で直接実装する       | 最大。homing・TMC2209 設定・安全機能を全部自前で持つ |

**推奨は C を目標にすること**。R1 と R2 を設計の中心に置けるのは C だけで、
RL の観測（位置・速度・荷重）も同じ周期で返せる。
ただし、段階 1 で A を実測し、要件を満たさないことを確かめてから着手する。
B は C の設計の参考と、C が行き詰まったときの代替として残す。

どの方式でも、SKR Pico をそのまま使う。塗布機と同じボードなので、予備と配線の知見を共有できる。

## 自作ファームの設計（方式 C）

### ハードウェアの割り当て

- **RP2040 のコア 0:** Pi との通信、指令の解釈、テレメトリの送信
- **RP2040 のコア 1:** 一定周期の運動ループ（速度の更新、加速度制限、ソフトリミット、接触判定）
- **PIO:** ステップパルスの生成。CPU の負荷とジッタから切り離す
- **TMC2209:** UART で電流・マイクロステップ・StallGuard を設定する。いまの `printer.cfg` の値を引き継ぐ
- **HX711:** 80 SPS のまま使い始める。不足なら ADC の交換を検討する（[未決定事項](#%E6%9C%AA%E6%B1%BA%E5%AE%9A%E4%BA%8B%E9%A0%85)）

台形ネジで最大 10 mm/s と遅いので、接触時はステップを即時に止めてよい
（減速を挟まない。homing と同じ止め方）。

### 状態

| 状態      | 意味                                     | 受け付ける指令                       |
| --------- | ---------------------------------------- | ------------------------------------ |
| `IDLE`    | 停止中                                   | すべて                               |
| `HOMING`  | 原点出し中                               | 停止                                 |
| `STREAM`  | 速度指令に追従中（R1）                   | 速度指令、停止                       |
| `MOVE`    | 目標位置への移動中（位置合わせ・搬送用） | 停止                                 |
| `CONTACT` | 接触で止まった（R2）。エラーではない     | 接触から離れる向きの指令、明示の解除 |
| `FAULT`   | ドライバ異常・通信断の繰り返しなど       | 明示の解除だけ                       |

`CONTACT` は停止した位置と荷重を報告し、ホストはそこから運転を続けられる。
`FAULT` だけが、Klipper の shutdown に当たる。

### 通信

- Pi とは USB CDC でつなぐ。フレームは連番と CRC を持つバイナリにする
- **指令:** 速度指令（各軸の速度と有効期限）、位置指令、原点出し、停止、`CONTACT` の解除、
    可動域・速度上限・接触しきい値の設定
- **テレメトリ:** 制御周期ごとに、位置（ステップ数）・速度・荷重・状態・最後に処理した指令の連番を返す。
    RL の観測と、遅延の監視に使う

### 安全

- **ウォッチドッグ:** 速度指令は有効期限を持つ。期限内に次の指令が来なければ、減速して停止する。
    ポリシーや Python が固まったときの安全装置
- **可動域と速度上限は MCU が持つ。** ホストがどんな指令を出しても超えない
- **接触停止は MCU の中で完結させる。** 風袋引きした荷重がしきい値を超えたら止める

## Pi 側（pcbasm）の構成

- **ピンセットのサーボ:** URT-2 経由で Pi から直接制御する。どの方式（A〜C）を選んでも変わらない。
    Feetech のバス・プロトコルは、LeRobot（SO-100/101）が使う STS3215 と同系で、ドライバの作りを参考にできる
- **ステージ:** 今の `XYZStage`（`pcbasm.hal.stage`）は Klipper と G-code を前提にしている。
    方式 C では、位置合わせ・駐機・立ち上げで使う「位置へ動く」操作と、R1 の速度指令を、
    新しいファームの上で提供し直す必要がある。どちらも HAL の境界に置き、`pcbasm.hal.fake` に fake を足す
- **併存:** 塗布機は Klipper のまま変えない。PnP 機だけ、ステージの裏側を差し替える
- **RL の環境:** HAL の上に、固定周期で行動を受け取り観測を返す環境を置く。fake の上でも動かせるようにし、
    テストとシミュレーションに使う

## RL の方針

- **RL に任せる範囲を絞る。** トレイから基板の上空までの搬送は、従来の位置決めで足りる。
    RL が効くのは、つかむ・置く直前の数 mm。範囲と速度を小さく限れば、安全層も単純になる
- **模倣学習から始める。** R1 の連続指令は、人がコントローラで操作するときのデータ収集にもそのまま使える。
    操作ログから模倣学習でポリシーを作り、そのあと RL で詰める
- **行動空間:** 速度または差分位置を、固定周期で出す
- **観測:** 2 系統のカメラ画像、ステージの位置と荷重、サーボの角度
