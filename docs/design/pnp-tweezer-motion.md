# ピンセット式 PnP の運動制御

部品実装（`[pnp]`）の機体の、運動制御の設計案。
XYZ ステージを動かすファームウェアと、ピンセットのサーボ、強化学習（RL）の置き場所を扱う。

ファーム（方式 C1）は `src/firmware/pnp-motion/` に実装した。実機での確認と、Pi 側（pcbasm）のクライアントはこれから。
XYZ は、Klipper の MCU ファームに速度指令のモジュールを足したもの（[方式 C1](#%E6%96%B9%E5%BC%8F%E3%81%AE%E6%AF%94%E8%BC%83)）で動かす方針とする。
言語は C とし、Zig は見送る（[言語](#%E8%A8%80%E8%AA%9E%E3%81%AE%E9%81%B8%E6%8A%9E)）。

## 前提

この機体は、一般の PnP 機のようにノズルとエアで部品を吸着しない。
**ピンセットで部品をつかみ、基板に置く**。人がピンセットで部品を置く動作を、機械で行う。

| 項目       | 構成                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| 自由度     | 4+1。XYZ と、ピンセットの回転（θ）で 4 軸、ピンセットの開閉で 1             |
| XYZ        | stepper。X・Y は inversed corexy、Z は直動。いまは Klipper で駆動する       |
| MCU        | BTT SKR Pico（RP2040、TMC2209 × 4）。塗布機と同じボード                     |
| θ・開閉    | Feetech STS3032 を 1 台ずつ。FEETECH URT-2 経由の UART で Raspberry Pi へ   |
| 接触の検知 | ロードセル（HX711、80 SPS）。いまは Klipper の `[load_cell_probe]`          |
| カメラ     | 2 系統。位置合わせ用のトップカメラと、ステージ全体を見渡すフロント RGB 広角 |

吸着ノズル・負圧・ノズル交換といった吸着式の概念は持ち込まない。
部品の保持と解放は、ピンセットの開閉（つかむ・離す）として扱う。

## 要件

- **R1 連続指令。** 「G-code を送り、着くまで待ち、止まる」ではなく、
    「速度 v で動き続け、指令が変わればすぐ従う」動かし方をしたい。
    人がコントローラで操作するのと同じ形で、機械も操作する
- **R2 接触停止。** ツールヘッドが何かに接触したことをロードセルで検知したら、即時に止める。
    これはエラーではなく、ただ止まる。止まったあとも、そのまま運転を続けられる
- **R3 RL で制御する。** 制御の多くを RL（と模倣学習）で作る。
    そのため、指令と観測が固定周期でやりとりでき、その遅延が一定であること

R1 と R2 は、RL のポリシーが何を出しても機体を壊さないための安全層も兼ねる。

### 数値で決める項目

次の値は未決定。表の「仮置き」は議論の出発点で、段階 1 の実測の前にユーザーと決める。

| 項目                       | 仮置き                          | 決め方                                         |
| -------------------------- | ------------------------------- | ---------------------------------------------- |
| 制御周期（指令・観測）     | 50 Hz                           | RL のポリシーの推論時間とカメラの fps で決める |
| 指令から動き出すまでの遅延 | 40 ms 以下で、ばらつきが小さい  | 学習時と実機のずれが出ない範囲                 |
| 接触から停止までの時間     | 20 ms 以下                      | 部品と基板を傷めない押し込み量から逆算         |
| 最大速度                   | 100 mm/s（今の `max_velocity`） | 機構で決まる                                   |

## Klipper のどこが要件に合わないか

Klipper は、Pi 側の Klippy（Python）と、MCU 側のファーム（C）に分かれる。
要件に合わないのは **Klippy** で、MCU ファームは R2 に要る部品をすでに持っている。
以下は Klipper `7bc4d094`（2026-09-28）のソースで確かめた。

### Klippy（Pi 側）

- **R1 に合わない。** 移動を「少し先の時刻」に予約し、先読みで速度をつなぐ。
    短い `G1` を流し続けると、バッファの分だけ遅延が積み上がるか、
    キューが空になって区間ごとに減速・停止する
- **接触停止を homing と probing の中でしか使わない。** トリガのあとは homing の後始末に入り、
    想定外のトリガは shutdown にする。任意の移動の途中で止めて、そのまま続ける経路がない

### MCU ファーム

MCU 側には、止める仕組みが汎用の部品として揃っている。

| 部品                               | 役割                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `trsync`（`src/trsync.c`）         | トリガで、登録した stepper をまとめて止める。`trsync_set_timeout` の期限が切れても止まる（ウォッチドッグに使える） |
| `stepper_stop_on_trigger`          | キューに積んだステップを捨てて即時に止める。**shutdown にはならない**。`reset_step_clock` のあと、続けて動かせる   |
| `stepper_get_position`             | 止まった位置（ステップ数）を返す                                                                                   |
| `trigger_analog` + `sos_filter`    | センサーの値を MCU の中でフィルタし、しきい値を超えたら `trsync` を引く                                            |
| `sensor_hx71x`                     | HX711 を読み、`trigger_analog` へ渡す                                                                              |
| `tmcuart`                          | TMC2209 の片線 UART                                                                                                |
| USB CDC（`src/generic/usb_cdc.c`） | 1200 baud で開くと ROM の bootloader に入る。BOOT ジャンパなしで書き換えられる                                     |

足りないのは、**速度指令から MCU の中でステップを作る部分**だけである。
いまは Pi が時刻つきのステップ列（`queue_step`）を送り、MCU はそれをなぞる。

ステップの速度は足りる。kurousagi（`microsteps: 64`、32 mm/rev で 400 steps/mm）の最大 100 mm/s では 1 軸あたり 40k steps/s。
corexy で X と Y を同時に動かすとモーター 1 つが最大 80k steps/s になり、3 モーターで約 200k steps/s。Klipper のベンチマークでは RP2040 は 3 軸で約 850k steps/s 出る。
PIO は使わない。

## 方式の比較

| 方式                                           | R1                                                      | R2                        | 新しく書くもの                   |
| ---------------------------------------------- | ------------------------------------------------------- | ------------------------- | -------------------------------- |
| A. Klipper のまま                              | 短い `G1` の連続送信で近似。遅延が課題                  | probing 中だけ            | なし                             |
| C0. Klipper の MCU ファームを無改造で使う      | Pi が速度指令を、短い先読みの `queue_step` に変えて送る | `trsync` で任意の移動中に | Pi 側のホスト（Klippy の代わり） |
| **C1. MCU ファームに速度指令モジュールを足す** | MCU が速度と有効期限を受け、自分でステップを作る        | 同上                      | C0 に加え、MCU に C で数百行     |
| C2. Klipper を手本に、ファームを書き直す       | 自由に設計できる                                        | 自前で実装                | ファーム全体（数千行の移植）     |

**C1 を採る。**

C0 は、Pi 側の遅れに弱い。Pi の処理が先読みの時間より長く止まるとキューが空になり、
そこへ過去の時刻から始まる `queue_step` が届くと `Timer too close` で shutdown する（`src/sched.c`）。
空になったかを Pi 側の時計で推測して `reset_step_clock` を挟むこともできるが、
まだ動いている stepper に `reset_step_clock` を送ると、これも shutdown になる。境目で競合が残る。
C1 は、加速度の制限と期限切れの減速を MCU が持つので、Pi の遅れはステップの途切れにならない。

C2 は、C1 で足りない点が見つかってから考える。
grblHAL（RP2040 版）も、ジョグと取り消しで R1 の大半を満たすが、移動中の接触停止は改造が要る。
Klipper の部品の方が R2 に近いので、採らない。

どの方式でも、SKR Pico をそのまま使う。塗布機と同じボードなので、予備と配線の知見を共有できる。

## 言語の選択

**C とする。** Zig は検討したうえで見送る。

| 観点             | C（Klipper の MCU ファームを元にする）                                                                                   | Zig                                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Klipper の再利用 | RP2040 のレジスタ操作、USB CDC、スケジューラ、プロトコル、stepper、trsync、HX711、TMC UART の約 5,000 行をそのまま使える | 移植が要る。C を `zig cc` でリンクはできるが、`DECL_COMMAND` は `buildcommands.py` がコンパイル結果のセクションを拾う仕組みで、`build.zig` へ移すのが手間 |
| 通信プロトコル   | Klipper のもの（VLQ、CRC16、連番、ack/nak）。コマンドの辞書をビルド時に作り、ファームが返す                              | comptime でコマンド表を作れる。ただし Pi 側の実装も自前                                                                                                   |
| 型と安全性       | タイマの wrap-around などは規約で守る                                                                                    | 整数のオーバーフローを検出し、wrap は `+%` で明示する。debug ビルドで境界チェックがある                                                                   |
| ホストでのテスト | 純粋なロジックを共有ライブラリにして、pytest から ctypes で呼べる                                                        | `zig test` がそのまま使える                                                                                                                               |
| ツールチェーン   | `arm-none-eabi-gcc`（Klipper の導入で Pi に入っている）                                                                  | 単一バイナリで導入が楽                                                                                                                                    |
| 安定性           | 安定している                                                                                                             | 1.0 前。0.15 → 0.16 で標準ライブラリの I/O を総入れ替えした。microzig も API が壊れると明記している                                                       |
| 保守             | Klipper の MCU 側は変化が遅く、upstream への追従が軽い                                                                   | 全部を自前で持つ                                                                                                                                          |

Klipper を手本にする以上、Zig の利点（comptime、安全性）が効くのは新しく書く部分だけになる。
C1 ではそれが数百行にとどまる。一方、Zig のコスト（移植、1.0 前の揺れ、Pi 側のプロトコルの自作）は全体にかかる。
Zig へ移るかは、C1 を作ったあと、Klipper から離れたくなったときに改めて決める。

## ファームの設計（方式 C1）

### 構成

Klipper の MCU ファームに、速度指令のモジュール `velocity_stream` を足す。
Klipper 本体への変更は、ビルドへの登録と、`stepper.c` の既存のコマンドの本体を関数として公開する
patch（`stepper_oid_lookup`・`stepper_queue_move`・`stepper_set_next_dir`・`stepper_reset_clock`・`stepper_position`）にとどめる。
コマンドの一覧とホストが守る前提は `src/firmware/pnp-motion/README.md` にある。

- **`velocity_stream`:** 一定周期（例: 2 ms）のタイマで task を起こし、各軸の目標速度へ加速度の制限つきで近づける。
    区間ごとのステップを `queue_step` と同じ形（先頭 1 歩と、`interval`・`interval + 1` の 2 段）で `stepper.c` のキューへ直接積む。
    stepper のキューを経由するので、`trsync` による停止と位置の数え方は Klipper のものがそのまま効く
- **kinematics:** 速度・可動域・可動域の手前の制動は、直交座標の X・Y・Z で計算する。
    計算した位置を、設定時に受け取る kinematics（cartesian・corexy・inversed_corexy）でモーターの位置へ写し、
    モーターごとにステップにする。corexy では、モーターごとの可動域では機体の矩形を守れないため
- **接触停止:** HX711 → `trigger_analog` → `trsync` → `stepper_stop`。`velocity_stream` も同じ `trsync` に
    シグナルを登録し、トリガで目標速度を 0 に戻す。止め方は homing と同じで、減速を挟まない
    （接触を探るときは遅く動かすので、即時に止めてよい）
- **原点出し:** Klippy と同じく、Pi が `endstop`・`trsync`・`queue_step` で行う。遅延の要件がないので、MCU 側に新しく書かない

### 状態

| 状態       | 意味                                                    | 受け付ける指令                       |
| ---------- | ------------------------------------------------------- | ------------------------------------ |
| `IDLE`     | 停止中                                                  | 設定、位置の設定、開始               |
| `STREAM`   | 速度指令に追従中（R1）                                  | 速度指令、停止                       |
| `STOPPING` | 目標 0 で減速し、積んだステップが出尽くすのを待っている | （出尽くすと `IDLE`）                |
| `CONTACT`  | 接触で止まった（R2）。エラーではない                    | 設定、位置の設定、開始（明示の再開） |
| `FAULT`    | Klipper の shutdown                                     | `FIRMWARE_RESTART` 相当の再起動      |

`CONTACT` は停止した位置を報告し、ホストはそこから運転を続けられる（荷重は Klipper の HX711 の報告で読む）。
どちらへ離れるかは MCU には分からないので、`CONTACT` のあとの速度指令は無視し、ホストが向きを決めて開始し直す。
`FAULT` は Klipper の shutdown をそのまま使う。
原点出しと目標位置への移動は、今のファームでは MCU の状態に持たない（原点出しは Pi が行い、位置への移動は Pi 側を作るときに決める）。

### 通信

Klipper のプロトコル（`docs/Protocol.md`）をそのまま使い、コマンドを足す。

- **指令:** 速度指令（各軸の速度と有効期限）、開始（`CONTACT` からの再開を兼ねる）、停止、
    可動域・速度上限・加速度・位置の設定。接触しきい値は Klipper の `trigger_analog` の既存のコマンドで設定する。
    位置指令（台形の加減速つき）は、Pi 側を作るときに足すかを決める
- **テレメトリ:** 制御周期ごとに、位置（ステップ数）・速度・状態・最後に受け取った指令の連番を返す。
    RL の観測と、遅延の監視に使う。位置は報告時刻の stepper の位置、速度は先読みの分だけ先の計画の速度
    （揃え方は Pi 側を作るときに決める）。荷重は Klipper の HX711 の報告で別に読む

### 安全

- **ウォッチドッグ:** 速度指令は有効期限を持つ。期限内に次の指令が来なければ、減速して止まる。
    ポリシーや Python が固まったときの安全装置。最後の砦として `trsync` の期限も張り、Pi が延長しなければ即時に止まる
- **可動域と速度上限は MCU が持つ。** 速度指令と位置指令は、可動域の手前で止まるよう MCU が制限する。
    原点出し以外では、Pi は生の `queue_step` を使わない
- **接触停止は MCU の中で完結させる。** Pi の Python で見張ると、Linux のスケジューリングで数十 ms の遅れが出得る

## ライセンスとリポジトリの構成

リポジトリは OSS で公開する。ハードウェアは CERN OHL で公開する予定。

| 対象                                   | ライセンス | 理由                                                                  |
| -------------------------------------- | ---------- | --------------------------------------------------------------------- |
| リポジトリの既定（pcbasm、WebUI など） | MIT        |                                                                       |
| `src/firmware/pnp-motion/`             | GPLv3      | Klipper（GPLv3）を元にするので、ビルドしたファーム全体が GPLv3 になる |

- **境界はディレクトリで示す。** ルートに MIT の `LICENSE` を置き、`src/firmware/pnp-motion/` には GPLv3 の `LICENSE` を置く。
    ファームの各ファイルの先頭には `SPDX-License-Identifier: GPL-3.0-only` を書く
- **pcbasm は Klipper のコードを取り込まない。** pcbasm とファームは USB 越しに話す別のプログラムなので、ファームの GPLv3 は及ばない。
    Klipper のプロトコルのクライアントは、`docs/Protocol.md` を仕様として読み、pcbasm に自前で書く。
    Klippy の `msgproto.py`・`serialhdl.py` は写さない
- **pcbasm からファームのコードを呼ばない。** fake や RL のシミュレーションで同じ運動の計算が要るときも、
    ファームの C を ctypes でリンクせず、Python で書く

### 置き場所

ファームは `src/` の下に置く。

```text
src/firmware/pnp-motion/
  LICENSE           GPLv3
  README.md         ビルドと書き込みの手順
  core/             Klipper に依存しない純粋なロジック（速度の更新、加速度の制限、
                    可動域の手前での制動、ステップ区間の計算）と、ホストで流すテスト
  module/           Klipper とつなぐ部分（velocity_stream.c。DECL_COMMAND、タイマ、trsync）
  patches/          Klipper 本体への小さな patch（ビルドへの登録、stepper.c の関数）
  skr-pico.config   Klipper の .config（menuconfig の結果）
  klipper/          upstream の Klipper（git submodule。commit を固定する。書き換えない）
  build.sh          klipper/ を build/ へ書き出して patch を当て、module を写して .uf2 を作る
  build/            ビルドの出力（Git で追跡しない）
```

- **Klipper は submodule で固定する。** どの Klipper を元にしたかを、リポジトリの履歴として持つ
    - `build.sh` は submodule を書き換えない。記録された commit を `build/` へ書き出し、そこへ patch を当ててビルドする
    - 機体の自己更新（`web.selfupdate`）は `fetch` → `merge --ff-only` で進み、submodule を動かさない。
        そのため `.gitmodules` に `ignore = all` を置き、submodule の版の違いを未コミットの変更と数えない（自己更新を止めない）。
        `build.sh` はビルドのたびに `git submodule update --init` で記録された commit に揃える
    - submodule は既定では取得しない。Klipper のソースが要るのはファームをビルドする機体だけで、`build.sh` が初めて取得する
- **Python のツールの対象から外す。** Klipper の `*.py` と `README.md` は、pyright・ruff の除外（`pyproject.toml`）と、
    `src` を走査するテスト（`tests/repo`、`tests/test_architecture.py`）の除外で、はっきり外す
- **`src/` の規約はファームにも効く。** pre-commit の `no-plan-references` は `src/` の下のテキストを検査する
- Klipper を fork したリポジトリを別に持つより、upstream の commit を固定して差分を patch で持つ方が、
    差分の大きさが一目で分かり、upstream に追従しやすい
- 既存のトップレベルの `klipper/`（塗布機の Klippy に足す拡張）とは別物である

## ビルドとデプロイ

- **ビルド:** CI では `core/` のテストを流す（`tests/firmware/`）。`.uf2` は Pi の上で `build.sh` でビルドする
- **配布:** `.uf2` はリポジトリに置かない。塗布機の Klipper ファームと同じく、導入時に Pi でビルドして書き込む
    （`./install.sh firmware pnp-motion`。中身は `deploy/firmware.sh`）
- **書き込み:** 初回だけ、今の手順（BOOT ジャンパ）で書く。以降は 1200 baud で bootloader に入れ、
    Klipper の `rp2040_flash` で書き換える。WebUI のジョブにできる
- **版の確認:** 接続時に、ファームの版（git hash とプロトコルの版）を確かめる。pcbasm と合わなければ動かさず、書き込みのジョブへ案内する

## PnP 機での Klipper の扱い

PnP 機には Klippy、Moonraker、Mainsail を入れない。`install.sh` で機種ごとに分ける。塗布機は今のまま変えない。

部品実装機の雛形 `deploy/templates/kurousagi/printer.cfg` から引き継ぐもの:

- kinematics（`inversed_corexy`）、X・Y・Z のピン、`microsteps: 64`、`rotation_distance: 32`、可動域
- TMC2209 の設定（片線 UART gpio8/9、アドレス X 0・Y 2・Z 1、`run_current: 0.4`、stealthChop）
- 原点出し: X・Y・Z ともリミットスイッチ（gpio4/3/25）。Z は正方向。順序は Z → X → Y
- HX711（gpio0/1、80 SPS）と、風袋引き・校正
- `led_light`（gpio17）

## Pi 側（pcbasm）の構成

- **ピンセットのサーボ:** URT-2 経由で Pi から直接制御する。ファームの方式と関係なく変わらない
- **MCU との通信:** Klippy の代わりに、Klipper のプロトコルを話すクライアントを pcbasm に置く。
    コマンドの辞書は接続時にファームから受け取る。Klippy のコードは写さず、自前で書く
    （[ライセンスとリポジトリの構成](#%E3%83%A9%E3%82%A4%E3%82%BB%E3%83%B3%E3%82%B9%E3%81%A8%E3%83%AA%E3%83%9D%E3%82%B8%E3%83%88%E3%83%AA%E3%81%AE%E6%A7%8B%E6%88%90)）
- **ステージ:** 今の `XYZStage`（`pcbasm.hal.stage`）は Klipper と G-code を前提にしている。
    位置合わせ・駐機・立ち上げで使う「位置へ動く」操作と、R1 の速度指令を、新しいファームの上で提供し直す。
    どちらも HAL の境界に置き、`pcbasm.hal.fake` に fake を足す
- **TMC2209 の設定と原点出し:** Klippy が担っていたものを pcbasm に移す。設定値は `machine.toml` に置く
- **併存:** 塗布機は Klipper のまま変えない。PnP 機だけ、ステージの裏側を差し替える
- **RL の環境:** HAL の上に、固定周期で行動を受け取り観測を返す環境を置く。fake の上でも動かせるようにし、
    テストとシミュレーションに使う

## RL の方針

- **RL に任せる範囲を絞る。** トレイから基板の上空までの搬送は、従来の位置決めで足りる。
    RL が効くのは、つかむ・置く直前の数 mm。範囲と速度を小さく限れば、安全層も単純になる
- **模倣学習から始める。** R1 の連続指令は、人がコントローラで操作するときのデータ収集にもそのまま使える。
    操作ログから模倣学習でポリシーを作り、そのあと RL で詰める
- **行動空間:** 速度または差分位置を、固定周期で出す
- **観測:** 2 系統のカメラ画像、ステージの位置と荷重、サーボの角度

## 進め方

各段階の確認のうち、実機を動かすものはユーザーが行う。

| 段階 | 内容                                                                                                          | 確かめること                                         |
| ---- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 0    | [数値で決める項目](#%E6%95%B0%E5%80%A4%E3%81%A7%E6%B1%BA%E3%82%81%E3%82%8B%E9%A0%85%E7%9B%AE)を決める         | 表の値がユーザーと合意できている                     |
| 1    | Klippy を止め、無改造の MCU ファームに Pi から直接つなぐ（C0）。1 軸を速度指令で動かし、接触で止めて再開する  | 接触から停止までの時間と、HX711 の 80 SPS で足りるか |
| 2    | ピンセットのサーボの HAL と fake を作る                                                                       | fake でのテストと、実機での開閉・回転                |
| 3    | `velocity_stream` を作る（`core/` とホストでのテストから）。`src/firmware/pnp-motion/` の構成とビルドを整える | 段階 0 の値を実機で満たす                            |
| 4    | Pi 側のステージを新しいファームへ差し替え、原点出しと位置合わせを動かす                                       | 既存の位置合わせのジョブが PnP 機で通る              |
| 5    | 遠隔操作でデータを集め、模倣学習と RL の環境を作る                                                            | つかむ・置くの成功率                                 |

段階 1 で作る Pi 側のクライアント（プロトコル、原点出し、`trsync` の扱い）は、段階 3 以降もそのまま使う。
段階 2 は、ほかの段階と関係なく先に進められる。
